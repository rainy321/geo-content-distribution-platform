# 豆包来源采集 MVP：调研、实现与验收

调研日期：2026-10-12。实现依据为本次提供的《豆包 GEO 来源采集与逆向分析系统：需求与技术方案》。本阶段交付单次消费者网页版采集器，不扩展营销、发布、Android 自动化或频率分析系统。

## 调研结论

1. **官方已有比通用豆包模型更接近客户端能力的接口。**“豆包助手 API”明确介绍其与豆包同源、提供 App 同款 AI 能力。通过 Responses API 的 `doubao_app` 工具可选择 `ai_search` 或 `reasoning_search`。它目前需要申请 beta 测试资格、开通服务及 API Key；HTTP 调用需要 `ark-beta-doubao-app: true` 请求头。它值得作为第二条验证路径，但文档没有保证同一问题的回答、来源列表、地区和个性化上下文与某次消费者会话逐项一致。[官方豆包助手文档](https://docs.volcengine.com/docs/ark/doubao-assistant?lang=zh)

2. **通用联网搜索接口适合补充检索研究。**Responses API 的 `web_search` 可以配置 `sources: ["doubao"]`；单独的豆包搜索接口返回候选网页的 URL、标题和摘要。候选网页与回答中的结构化引用必须分开保存，且都不能标成消费者 UI 引用。[联网搜索工具](https://docs.volcengine.com/docs/ark/web-search?lang=zh)、[豆包搜索 Custom 版](https://docs.volcengine.com/docs/87772/2272953)

3. **网页版已完成真实问答与来源验证。**本机通过普通 Playwright/Chromium 和专用持久化会话向豆包消费者网页提交公司项目问题，取得完整回答。随后只读重开同一对话，核对回答原文并展开 UI：提取 24 条资料列表链接，以及 1 条正文引用的实际点击跳转地址。初期出现过人机验证、会话重定向和临时网络断开；用户正常登录后，公司实验没有再触发人工等待。来源核对没有重复提交问题。

4. **暂未确认公开、无需资格且复现消费者会话的官方接口。**豆包开放平台介绍 OpenAPI，但首页标明内测；不能据此假定已有可直接使用的消费者聊天历史/引用接口。私有网页接口签名、App 抓包和第三方代理均不作为第一阶段实现。[豆包开放平台](https://open.doubao.com/)

5. **显示来源的范围有上限。**豆包用户协议说明：识别联网搜索意图或主动选择 AI 搜索后，会检索第三方公开信息并展示搜索来源。由此可以采集“用户可见来源”，无法证明抓到了全部内部召回网页。条款也对服务内容的爬取等使用作出限制，生产或批量运行前需明确适用权限；本实现只提供一次低频验证，不启动无人值守批量任务。[豆包用户协议](https://www.doubao.com/legal/terms)

## 第一阶段实现

- `services/doubao_source_collector.py`：单次采集、UI 状态识别、来源提取、截图、DOM 快照和证据摘要。
- `services/doubao_source_cli.py`：`collect` 和 `login` 两个入口，安装后也可使用 `geo-doubao`。
- `tests/test_doubao_source_collector.py`：完成状态、防误收链接、来源去重、缺失 URL、来源展开失败和证据校验。

一次执行只按一次 Enter。登录、人机验证、会话被重置或频率限制均不自动重试。普通浏览器配置不注入反检测脚本，不直接调用私有端点，不读取或导出用户日常 Chrome 的 Cookie。

### 安装和运行

项目现有 `[web]` 可选依赖已包含 Playwright；本次没有新增第三方依赖。若尚未安装：

```powershell
uv pip install -e ".[web]"
.venv\Scripts\python.exe -m playwright install chromium
```

实验对象已按项目所有者要求调整为：公司「北京同于野科技有限公司」，项目「懂AI中转站」。默认问题为：

> 北京同于野科技有限公司的懂AI中转站是什么？请结合可查询到的公开网络信息介绍其功能；如果资料不足，请明确说明。

这属于明确给出品牌名称的认知实验；不能用它证明用户未提及品牌时，豆包会主动推荐该项目。回答涉及的功能、官网、公司与项目的关系仍需与实际公开资料核对。

项目所有者已提供官网 [tongyuye.com](https://tongyuye.com/)。公司、项目、官网、事实依据与问题条件保存在 [公司实验记录](./experiments/tongyuye-dongai.json)。原始问题没有提供域名，保留为品牌名称实验，不用后来获得的网站资料改写历史回答。

单次真实采集：

```powershell
.venv\Scripts\python.exe -X utf8 -m services.doubao_source_cli collect --timeout 180
```

需要正常登录/验证时先打开**专用**浏览器；在页面中由用户处理，完成后关闭页面：

```powershell
.venv\Scripts\python.exe -X utf8 -m services.doubao_source_cli login --login-wait 300
.venv\Scripts\python.exe -X utf8 -m services.doubao_source_cli collect --headed --timeout 180 --manual-wait 300
```

专用会话默认保存于 `runtime/doubao/browser-profile/`，证据默认保存于 `runtime/doubao/evidence/<run_id>/`。`runtime/` 已被 Git 忽略。`--profile-dir`、`--output-dir` 可调整目录；不要把包含登录会话的 profile 或私人截图上传仓库。

`--manual-wait` 只等待用户在当前窗口正常验证/登录，不填写验证码、不重新发送问题。等待总预算最多 600 秒，与回答生成超时分开计算；等待事件和截图进入证据记录。未开启或预算耗尽时仍返回 `need_action`。

Windows、Linux 均使用相同入口。Linux 无头模式需先安装 Chromium 系统依赖，例如 `python -m playwright install --with-deps chromium`。首次正常登录可能需要显示环境；在容器中只挂载这个专用 profile 和证据目录，使用非 root 用户、串行单进程。当前阶段不把采集器部署到 Vercel，也没有自动启动采集服务。

### 页面变化时的选择器

已实测当前页面的输入框、用户/助手消息、`message_text_content`、`message_action_copy`、`search_query_result_block` 资料入口、`data-thinking-box-tool-call` 来源链接及无 `href` 的正文引用标记。当前正文引用使用生成的 CSS 类名 `container-sWvQla`，页面更新后尤其需要复核。其他候选变体不代表已验证的 UI 协议。程序支持 `--selectors <JSON文件>` 局部覆盖。

例如，在实际浏览器中确认相应元素后，提供配置：

```json
{
  "assistant_message": "实际助手消息容器的 CSS 选择器",
  "answer_text": "容器内实际正文的 CSS 选择器",
  "completion": "容器内实际完成操作的 CSS 选择器",
  "source_trigger": "该回答的来源入口 CSS 选择器",
  "source_panel": "来源面板的 CSS 选择器",
  "source_card": "面板内来源卡片的 CSS 选择器"
}
```

正文选择器必须位于助手消息内，完成标识必须对应当前回答。静默几秒或网络连接空闲不能证明流式输出已完成；实现同时要求新助手消息、问题出现在用户消息中、完成标识出现、没有生成中标识、正文持续稳定。找不到这些信号则记录超时/选择器变化。

正文引用仅来自明确的正文引用元素；资料列表来自当前回答的来源入口。导航、历史记录、普通正文链接和模型自述链接不进入这两类统计。URL 取自实际 `href`，或点击明确的正文引用后观察到的新标签页导航；不按网页标题搜索补链，不解码重定向参数猜测目标，也不将第三方网页的可访问性作为引用真实性依据。

标题只有普通 UI 标签时，记录 `title_kind=ui_label`；有明确标题元素时才为 `ui_title`。无 `href` 的正文引用会保存悬浮卡片截图，并通过一次正常点击观察新标签页地址；`ui_href` 仍为 `null`，`url_observation_method=ui_click_navigation`。不能取得可验证地址时保留 `url=null`，不补造链接。导航观察不保证第三方页面能打开或内容准确。

### 输出与证据

`result.json` 保存问题、时间（UTC+08:00）、原始回答、提交尝试/用户消息观测状态、回答是否完成、正文引用、显示资料列表、非敏感环境信息、异常原因和截图文件名。当前自定义 schema 为 `1.1`。

| 字段 | 含义 |
| --- | --- |
| `client=web` | 消费者网页版；不能与官方 API 样本合并标记 |
| `source_scope=client_displayed` | 仅记录被当前 UI 展示、被采集器识别的来源 |
| `retrieval_results=null` | 内部候选召回列表不可观测，不将未知填成空列表 |
| `api_citations=null` | 本次未调用官方 API |
| `citations` | 正文中明确显示的引用标记；与资料列表分别去重 |
| `displayed_sources` | 当前回答 UI 展示的资料条目，不推断每条都被正文引用 |
| `evidence_type=ui_citation` | 有明确正文引用元素；可以保存对应段落原文 |
| `evidence_type=ui_source` | 来源面板中的显示条目；不推断它必然被某个句子引用 |
| `linked_answer_text=null` | UI 未提供可验证的正文对应关系 |
| `visible_citation_count` | 已提取的唯一正文引用数量；未采集时为 `null` |
| `ui_citation_count` | 同上述正文引用数量，兼容已有字段 |
| `visible_source_count` | 已提取的唯一资料列表条目数量；未采集时为 `null` |
| `source_ui_summaries` | 页面原样显示的搜索/参考资料摘要，不推断内部召回总量 |
| `source_extraction_status=none_detected` | 没检测到匹配的来源，仍需结合 UI/选择器核验，不能证明来源不存在 |
| `source_extraction_status=incomplete` | 存在来源入口但展开/解析不完整，不能统计成零引用 |

每次保存 `before`、`question`、`answer` 或 `failure` 截图与相关 DOM 快照。用户消息首次出现时保存 `submission-observed.json`。来源展开另存截图/DOM；无链接引用另存悬浮卡片截图、标记 DOM 和 UI 点击导航地址。同一 URL 出现多次时保留对应段落和全部证据文件。`evidence_manifest` 为原始文件计算 SHA-256，便于检验之后的文件变化；摘要不是第三方签名，也不能单独证明服务器曾使用某条来源。

| 退出码 | 状态 | 处理 |
| --- | --- | --- |
| `0` | `success` | 回答完成且未遇到已知来源提取失败；仍按下面要求审阅真实性 |
| `1` | `failed` | 查看失败阶段、截图和 DOM，区分网络/页面变化/超时 |
| `2` | `need_action` | 正常登录/验证/等待限流，不自动重新提问 |
| `3` | `partial` | 回答完成，但来源提取不完整 |

## 端到端验收与当前状态

公司项目验收使用上面的默认问题，并保存原文；不追加“请自己列出 URL”，避免引入模型自述来源。

1. 确认真实页面 URL、问题截图和提交后用户消息 DOM；客户端出现问题只证明页面显示，不能单独证明后端完成处理。
2. 取得当前问题对应的完整回答、完成标识和截图。
3. 若展示来源，至少一条标题/URL 能在来源截图与 DOM 中逐项核对；标题-only 条目不得补造 URL。
4. 若没有匹配来源，审阅页面与选择器，区别“确实未展示”“入口未展开”“选择器失效”。
5. 失败也必须保存原因与证据；`success` 程序退出码不替代人工的首次真实性验收。

本次真实访问证据：

- 首次页面/输入/人机验证截图位于 `.tmp/doubao-probe/`，属于真实访问，不是测试 fixture。
- 初版完整证据目录为 `runtime/doubao/evidence/20261012-143240-52db7705/`；提交后重定向到 `from_logout=1`，且采集时遇到页面执行上下文重建。已针对导航重建增加只读恢复，并增加会话重定向识别。
- 公司项目真实问题与完整回答保存于 `runtime/doubao/evidence/20261012-153606-efa9a960/`。当时资料入口和正文引用选择器尚未适配，初版 JSON 的零来源不是“豆包没有来源”的证据。
- 按真实 DOM 修正选择器后，只读打开同一对话，匹配同一用户问题与回答原文，再保存来源复核证据于 `runtime/doubao/evidence/20261012-154848-source-inspection/`。该目录记录 `mode=inspect_existing_answer`，关联原采集结果，未重新提交问题。结果：完整回答 711 字符、24 条资料列表、1 条正文引用；已验证该引用正常点击后打开的完整 URL。
- 真实消费者问答及至少一条 UI 来源的最小验证已完成。尚未实测官方 API 或 Android，也未测试无人值守批量稳定性。

### 公司实验的初步观察

豆包本次回答表示，公开资料不足以确认「北京同于野科技有限公司」与「懂AI中转站」的运营关系或产品功能。这只是本次回答的观察结果，不代表项目不存在，也不证明所有搜索入口都没有资料。

显示资料中可见水滴、启信宝等目标公司的企业信息页，也包含泛行业新闻、名称相近的「北京同人于野科技有限公司」及其他无关资料。不能将资料列表中的名称近似匹配直接统计成目标公司的曝光。正文唯一明确引用的「中国新闻网」对应行业风险提示段落，并非项目功能介绍或品牌推荐。本轮问题已给出公司和项目名称，因此也不能据此判断无品牌提示时的主动推荐能力。

#### 官网核对（2026-10-12，更新前快照）

用户提供域名后，在本机通过普通 HTTPS 请求和 Chromium 分别核对公开首页：HTTP 200，页面标题「懂AI · 统一模型聚合与中转站」，描述「懂AI — 统一模型接口与人民币用量平台」。页面公开介绍了统一模型网关、OpenAI 兼容接口、线路容灾、人民币计费、调用审计和 Agent 工作台等能力。这些是官网公开自述，尚未用真实 API 调用验证其实现或服务质量。[官网](https://tongyuye.com/)

原始首页 HTML 的正文只有 `root` 挂载节点，介绍内容由 JavaScript 渲染；本次检查的渲染后首页正文没有出现「北京同于野科技有限公司」全称。公司与项目的对应关系目前来自项目所有者说明，不能把它写成“已在官网确认公司主体”。初始 HTML 的空正文可能影响部分抓取器读取，但尚不能据此判定豆包没有检索到官网的原因。

已逐条检查前次 24 条显示资料和 1 条正文引用，其中没有 `tongyuye.com`。官网确实可访问，因而前次豆包的“未找到公开资料”需要作为一次检索遗漏或未命中观察保留，不能当作官网不存在的证明。网页工具的两次 `site:tongyuye.com` 搜索没有返回结果，也不等同于所有搜索引擎均未收录。

普通请求下 `robots.txt` 返回 404，这本身不代表禁止抓取；`sitemap.xml` 请求遇到连接/TLS 中断，未确认其存在与否。上述原始 HTML、浏览器正文、DOM 与截图保存在 `runtime/doubao/site-verification/tongyuye-20261012/`。

## 实验偏差与下一步

本次显示的模型标签为「豆包 快速」，底层版本未知。后续重复实验保存问题原文、客户端、时间、显示的模型名称、未知版本、地区来源、会话条件及是否新建对话；不把浏览器时区当成真实出口 IP 地区，也不把页面标签推断为底层模型版本。浏览器导航只对明确的临时连接断开重试一次，已提交的问题从不自动重发。

API 对照单独采样，保留原始结构化响应、实际请求模型/功能、返回引用及调用状态。Android 只有在研究移动端特有展示差异时才增加。第一阶段使用文件保存而非数据库、队列和管理后台，减少需要维护的组件；不依据一次结果估算稳定引用频率，也不从来源频率推断发布效果因果关系。
