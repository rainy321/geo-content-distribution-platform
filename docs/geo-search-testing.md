# 通用客户 AI 搜索测试

本模块把单次豆包来源采集扩展为：客户资料 → AI 生成固定问题 → 独立新对话串行采集 → 分组报告。客户可以来自软件、工业、教育、服务等行业；问题由实际 AI 根据资料生成，没有按行业硬编码问句。当前执行平台是豆包网页版，消费者对话和工作界面明确记录，其他平台尚未实现。运行范围每轮 3–12 题，默认 4 题、间隔 15 秒。

## 客户资料与问题设计

客户资料支持 `name`、`product`、`company`、`industry`、`description`、`keywords`、`competitors`、`audience`、`region`、`aliases`、`website`。名称和行业/业务说明是必填信息，其余可留空；没有官网时不生成官网问题。资料属于客户自述，不能作为已验证事实。品牌别名应由客户明确提供；相似公司名不自动视为别名。

新资料还支持 `entity_type`（`company` 或 `product`）和 `official_urls`。公司与产品分别建项目、生成计划并记录基线；别名只填写当前测试对象的明确名称。产品资料中的 `company` 是运营关系背景，回答只出现该公司不计产品提及；报告另行显示公司提及。产品核验题必须点名产品，不能只点名运营公司。自然发现题仍禁止泄漏产品、公司、别名或全部官方网址的域名。

官网命中按主网址和明确配置的 `official_urls` 核对：主机和端口准确匹配，非根路径按完整路径段限定。同一主站的 `/about/`、其他产品页或另一个子域，不会自动算作当前产品的官方引用。所有官方范围保存在计划快照中；范围或测试对象改变时需要新基线，不能直接混算复测。没有 `entity_type` 的旧计划保留原指纹和历史宽口径，并在报告标注，不能冒充新方法的基线。

### 同于野：公司与两个产品

2026-10-20 读取官网后，按以下三个对象分别配置。产品能力来自官网自述，尚不等于软件独立功能验证。

| 测试对象 | 主网址与范围 | 自然需求方向 |
| --- | --- | --- |
| 北京同于野科技有限公司 | [公司官网](https://tongyuye.com/)；公司主体与业务 | 企业 AI 应用建设、模型接入、智能体开发及系统集成服务商 |
| 懂AI中转站 / 懂AI DongAI | [产品页](https://tongyuye.com/products/dongai/)；另登记官方链接的 [API 服务入口](https://api.tongyuye.com/) | 开发团队的多模型 API 接入、密钥和用量管理 |
| 同于野软件 / 同于野桌面客户端 | [桌面产品页](https://tongyuye.com/products/tongyuye/) | 资料研究、内容写作、文件和网页协同的 AI 桌面软件 |

每个对象各自执行自然发现、点名核验和官网引导三类问题。问句仍由 AI 根据资料生成并经用户确认，不把手写示例标为 AI 出题；本次调整方法和配置本身也不是新的真实采集结果。旧中转站报告继续保留在原项目，不因公司官网改版而改写历史网址或提及率。

可审阅的资料文件分别为 [公司](experiments/tongyuye-company-profile.json)、[懂AI产品](experiments/dongai-product-profile.json) 和 [同于野桌面软件](experiments/tongyuye-desktop-profile.json)。

AI 返回的 JSON 经过数量、类别、重复问题、名称/域名泄漏等校验；校验失败会明确报错，不用模板问题冒充 AI 输出。默认 4 题在有官网时分配为 2 个行业问题、1 个品牌问题和 1 个官网问题。计划生成后保存客户资料、问题原文、AI 生成方式和 SHA256 指纹；复测用同一份计划开启新的运行目录。

首次实测后加强了生成指令：至少一道行业发现问题要求给出公开可核验的候选产品/方案/服务商，避免所有问题都只询问通用方法。已经生成的计划保留原文，不在看到回答后改题并混为同一轮。

| 类别 | 题目条件 | 报告含义 |
| --- | --- | --- |
| `discovery` | 不出现品牌、产品、公司、别名、官网域名 | 本轮自然提及观察 |
| `brand_identity` | 点名品牌，询问公开业务及运营主体 | 品牌核验结果，不能算成自然曝光 |
| `website_guided` | 提供完整官网网址，请求核验 | 指定网址可读性与公开说明核验 |

同一 AI 搜索助手可以生成计划并执行测试，但计划生成记录只属于问题设计证据，不能混入曝光统计。提供官网的题目明确要求无法访问或无法确认时说明。

## Web 工作区

Windows 用户也可直接使用独立窗口的 [GEO AI 搜索工作台](desktop-app.md)。桌面版提供“登录豆包”“用豆包生成问题”“开始测试”和“停止任务”按钮，不需要复制采集命令；浏览器版保留本机命令执行方式。

Windows 本地使用可直接双击仓库根目录的 `start-geo-tests.bat`：启动已有前端构建与本机后端，自动打开“AI 搜索测试”和最近一份完整报告。后端只监听 `127.0.0.1`，启动入口不启用发布调度。退出浏览器不关闭后台服务，再次双击会复用已运行服务。

页面的“已保存报告”自动读取本机 `runtime/geo-tests/` 下的报告，点击选择即可查看，无需手动找 JSON 文件。报告接口沿用工作区访问控制，只允许读取扫描到的报告 ID，不接受任意文件路径。部署到其他机器时，该列表只包含那台机器上的报告。

侧栏新增“AI 搜索测试”（`/#/geo-tests`），复用“品牌项目”中的资料，可补运营公司与目标客户。AI 接口配置复用系统设置：API Key 只随当次请求发送，不写入计划或报告。生成计划后可审阅、下载；没有 API 配置时导出客户资料，用本机已登录的豆包生成计划。

采集在本机执行，不放进 Vercel 的短时请求或公开浏览器进程。采集结束后，页面支持导入 `report.json`，按三类分别展示分母、品牌提及、官网资料/引用命中及完整回答。也可导入 CLI 生成的 `plan.json` 查看问题。导入文件只在当前页面内存中使用。

`POST /api/geo-tests/plan` 请求示例：

```json
{"project_id": 1, "case_count": 4, "company": "运营公司名称", "audience": "目标客户"}
```

缺少资料返回 400，项目不存在 404，AI 配置缺失 503，AI 输出不合格/服务失败 502。接口沿用工作区登录和 AI 请求限流。

## 本机执行

需要安装项目依赖及 Playwright 浏览器，步骤见[单次采集说明](doubao-source-collection.md)。以下 PowerShell 命令在仓库根目录执行。

先生成实际 AI 计划，支持 OpenAI-compatible API（读取 `AI_BASE_URL` / `AI_API_KEY` / `AI_MODEL`）或消费者豆包会话。没有有效配置不会执行离线替代并称其为 AI。

```powershell
# API 生成：也可用 --project-id 1 --database db/database.db 复用品牌项目。
.venv\Scripts\python.exe -X utf8 -m services.geo_test_cli plan --profile client-profile.json --output plan.json

# 豆包生成：先在专用窗口完成正常登录，然后关闭窗口保存会话。
.venv\Scripts\python.exe -X utf8 -m services.doubao_source_cli login --login-wait 600
.venv\Scripts\python.exe -X utf8 -m services.geo_test_cli plan --profile docs/experiments/dongai-product-profile.json --planner doubao-web --output runtime/geo-tests/dongai-product-plan.json --headed

# 审阅计划后，执行整轮；每题新建对话，默认间隔 15 秒。
.venv\Scripts\python.exe -X utf8 -m services.geo_test_cli run --plan runtime/geo-tests/dongai-product-plan.json --run-dir runtime/geo-tests/dongai-product-run-001 --headed

# 正常登录/验证恢复后，仅继续可安全执行的未提交问题。
.venv\Scripts\python.exe -X utf8 -m services.geo_test_cli resume --run-dir runtime/geo-tests/dongai-product-run-001 --headed
```

`--case-count` 只用于计划生成；`--timeout` 控制每题回答等待；`--cooldown` 允许 10–300 秒。`--manual-wait 300 --headed` 可保留当前页面等待用户正常验证，预算上限 600 秒。退出码：0 完成，1 配置/输入/计划错误，2 采集停下、存在缺口或需要检查。

本次账号登录后进入“豆包工作”，普通界面选择器仍可读取消息、完成标记和 JSON 计划。针对这个界面，需要在 `plan`、`run`、`resume` 中显式传 `--client-mode work`，通过正常“新工作任务”按钮新建对话；默认 `consumer` 用“新对话”。检测到界面类型不符就停止，不能静默换模式。工作界面实际显示的模型标签为“自动 / 高”，底层版本未知，不能与之前“豆包 快速”结果直接当作同条件对照。恢复任务必须保持原界面类型。

工作界面“自动 / 高”的第一轮出现容量提示和超时，另开一轮通过正常菜单选择当时可用的 `--model-label "豆包 2.1 Lite"` 后完成了三题。选择只允许唯一匹配且可用的菜单项，不点击“升级”或不可用选项；结果同时记录请求的选项和实际显示标签。更换模型必须开新轮，不能在恢复时混入旧轮。此观察不代表 Lite 在所有账号/时段都稳定可用。

## 执行与报告边界

每轮目录包含 `plan.json`、原子写入的 `state.json`、`report.json` 和逐题 `evidence/`。底层采集证据包含截图、DOM、原始回答/来源和文件哈希。计划、客户资料与会话应保存在被 Git 忽略的 `runtime/`，不能共享浏览器配置目录。

`question_submitted` 表示 UI 已显示匹配的用户消息，不等于服务端已经成功处理。如果验证发生在请求落地之前，页面可能只有临时 `local_...` 会话；此时必须保留当前窗口供用户正常验证，不能依据这个临时地址声称可以重开恢复答案。完成验证后程序继续同一条消息，不会再按 Enter。

执行器按串行运行，在提交前持久化 `running`，使用操作系统文件锁阻止两个任务同时使用同一会话。登录按钮、验证码、退出登录、限流或采集失败会停止当前批次；不会靠自动重发来补次数。恢复时，仅重试明确记录为“没有尝试提交”的失败问题，已提交过的问题保持原结果。进程中断留下 `running` 或采集器异常且提交状态未知时，标记 `needs_review`，需要先核对证据，不能自动重发。

报告的品牌提及是原文大小写/空白归一后的名称匹配，保存对应原文片段。否定、资料不足同样可能包含名称，因此 `recommended` 和 `fact_accuracy` 当前保持未知。行业问题的提及率只以匹配题目且完整回答的问题为分母；失败、未提交和未完成答案不算零曝光。公司名近似匹配不算目标公司。

正文引用与界面搜索资料分别统计，官网匹配只认真实 URL 的 hostname 和子域名，忽略网址正文里的提及、查询参数和伪造后缀。来源提取不完整且没观察到命中时保持未知；`none_detected` 也不能单独证明没有来源。报告展示来源可判断数量，避免把缺失数据误算成 0。UI 搜索资料不能代表全部内部检索结果。

部分引用只有来源站点名；在当前工作界面，通过正常悬停可见的引用卡片，校验卡片站点与当前标记一致，再点击卡片标题观察新标签页 URL。鼠标移动时卡片可能切换，因此同时校验实际点击瞬间的标题和站点；新标签页还需以公开文档标题对应引用标题，错配或无法对应时保留未知，导航地址只存检查证据。登录跳转、打不开或标题差异也可能导致地址暂不确认。卡片选择器需在 UI 更新后复核。网址无法观察时保留空值，不能由标题推测；只要存在未解析网址，就不能据此证明官网没有被引用。容量提示也可能带“复制”按钮，因此“算力紧张，办公能力得晚点才能用了”已被识别为服务失败，不计入回答分母；旧记录的报告同样会排除这种提示。

一轮 1–10 个行业问题是功能验证，不是稳定曝光率、搜索排名或优化效果的证据。新对话减少上下文串题，但账号个性化/模型变化仍可能影响结果。模型版本未知就保持未知；浏览器时区不能证明出口 IP 地区。跨日期比较保持同一份计划，后续应增加独立重复轮次、模型/账户记录以及优化前后对照。
